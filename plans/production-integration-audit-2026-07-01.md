## 1. Database (PocketBase) integration

### 1.1 🔴 CRITICAL — "Add new hire" silently fails via the normal click path

**Repro:** As a Game Maker, Admin Home → "Add new hire" → type a name → "Create". Expected: land on the new hire's Customize tab (`AdminHomePage.tsx:160` calls `navigate(/admin/${sid}/hire/${newSessionId}?new=1)`). **Actual:** the modal closes and you're dropped back on the same empty "No new hires yet" Admin Home. No error, no toast. Reproduced twice in a row, 2/2.

**Root cause:** `src/pages/hire-detail/useHireDetailPage.ts:214-218` —

```ts
useEffect(() => {
  if (sessionError && !sessionLoading) {
    navigate(`/admin/${homeSid}`, { replace: true });
  }
}, [sessionError, sessionLoading, navigate, homeSid]);
```

Network trace shows the client-side transition into HireDetailPage fires `getSession`/`listMilestones`/`listMissions` for the brand-new session at the same moment `AdminHomePage`'s own `useGmHires` refresh (triggered by `createHire`) is *also* fetching milestones/missions/players for every owned session, including the new one, to recompute `joined`/progress. Two calls to the identical PocketBase REST URL in flight at once trip the JS SDK's default **auto-cancellation** (`new PocketBase(PB_URL)` in `src/adapters/pocketbase/mod.ts:11` uses no `requestKey`/cancellation override), one gets aborted (`NS_BINDING_ABORTED` in the network log), `useSession`'s `Promise.all` rejects, `sessionError` is set, and the effect above bounces you straight back out. A **hard reload** of the exact same `/admin/:sid/hire/:hireId?new=1` URL loads fine every time — confirming it's a race between two hooks, not a data problem. The session itself, and its data, are created correctly (`POST /api/collections/sessions/records` → 200, `qrSecret` genuinely generated by the Go `OnRecordCreate` hook).

**User-facing effect:** every single "Add new hire" click currently dead-ends. The hire is invisible afterward too, because `AdminHomePage.tsx:169` filters the list to `hires.filter(h => h.joined)` — an un-joined hire (correct, by design) simply disappears with no affordance to find it again except knowing the URL.

**Fix direction:** give each hook site its own `requestKey` (PocketBase SDK supports passing `{ requestKey: null }` to opt a call out of cancellation, or a unique key per caller), or stop `useGmHires`'s per-session detail refetch from racing the just-created session's own detail fetch (e.g., skip re-fetching a session's milestones/missions in the hires list until the hire-detail page has settled, or debounce/sequence the two).

### 1.2 🟠 Two parallel invite mechanisms exist; the live one skips the token entirely

The codebase has real, working code for a token-gated invite claim: `generateInviteToken()`, `buildInviteUrl()` (`src/utils/inviteUrl.ts`), `claimPlayerSlot()` (`src/use-cases/joinSession.ts:78`), and an auto-claim effect in `useLandingFlow.ts:130-157` that reads `?token=` on `/join/:sessionId` and calls `adapter.getPlayerByInviteToken`. This is legitimate, wired code — not a stub.

But the actual UI the admin uses, `SessionInviteCard.tsx:59` (rendered from `HireInviteAccordion.tsx`'s "Send {name} their onboarding link"), builds the shared link as `${origin}/join/${sessionId}` with **no token at all**. Since `useLandingFlow` only attempts the claim when both `routeSessionId` *and* `token` are present, the entire claim path never fires from the real invite button — it only prefills the session code into the manual "Employee" join form (`joinSession()`, a brand-new player, not a claimed slot). Net effect: the invite link *does* work (verified: lands the player in the right session, `joinSession` creates a real PB player record), but the token/pending-slot machinery — and whatever admin-side pre-configuration was meant to travel with it — is 100% dead code in the current UI. If the two were ever meant to be the same feature, they've drifted apart.

**Fix direction:** either wire `SessionInviteCard` to call `buildInviteUrl(sessionId, token)` with a token minted via `generateInviteToken()` + a pre-created pending Player row, or delete the token/claim code path if the simpler flow is now the intended design — right now it's ambiguous which one is "real."

### 1.3 🟡 Stale/orphaned local identities fail silently

Visiting `/session/:id` (or clicking "Resume as…") for a profile whose session no longer exists in PocketBase (e.g. after a DB reset) 404s on `getSession` and the page just redirects to `/` with zero explanation — the dead profile stays in the picker, inviting the user to click it again and hit the same silent failure. Not a new code bug so much as a missing error state; worth a "This session could not be found — remove this profile?" message instead of a silent bounce.

### 1.4 ✅ Confirmed working

- Real PocketBase is genuinely used for non-demo sessions (verified via network trace, not `window.__MB_CONFIG__` alone — that config only covers the LLM proxy, not `useMockPb`).
- `DemoAwareAdapterProvider.tsx` correctly switches per-profile: any profile with `isDemo: true` for a given `sessionId` routes that session to `mockAdapter`, everything else to real `pbAdapter`. This resolves the ambiguity flagged in the prior live-deploy memory ("useMockPb:false but rendering seed data") — it isn't a config bug, it's this by-design per-profile switch, since `sess_mmt2026` is always a demo session regardless of the global build flag.
- Session creation, `qrSecret` generation (Go migration hook), and template listing all hit real PocketBase and behave correctly (templates list is genuinely empty in production — matches known gap G-11, not a bug).

## 2. AI Assistant integration

**Verified working, but with a real intermittent failure mode.**

Sent two real questions to Sofia Chen's assistant tab (`/llm/v1/chat/completions`, real LiteLLM + pgvector RAG + reranker, not mock — `useMockChat: false` confirmed via `window.__MB_CONFIG__`):

- "How many vacation days do I get?" → correctly returned the grounded "not in the documents… contact HR" fallback (correct behavior, per system-prompt guardrail).
- "Can I work from home?" → correctly returned a grounded, cited answer from the real docs.

Both requests eventually returned `200` with a well-formed SSE stream. **But the first question displayed "I didn't get a response. Please rephrase or try again shortly." in the UI**, even though the network trace shows the backend's response — captured after the fact — contained the correct answer text. The second question (same session, immediately after) succeeded and rendered normally. Total time-to-completion for both requests was ~15–25 seconds, which is the likely cause: `src/hooks/useChatStream.ts` has no explicit client-side timeout, but a cold reranker/RAG pass on the first request in a session appears slow enough that the failure surfaces before the stream is read as expected. This is a different symptom than the previous live-deploy finding (a hard `500`) — the backend is not erroring here, it's just slow, and the UI's handling of a slow-but-eventually-successful stream produces a false "no response" to the user.

**Fix direction:** either accept and communicate the latency (e.g. "Thinking… this can take up to 30s" instead of the generic spinner), or investigate why `reader.read()` in `useChatStream.ts:188-198` appears to terminate before content arrives on slow first requests — worth adding a repro harness that logs each `read()` chunk with a timestamp rather than relying on UI polling.

## 3. QR code generation + validation

**Verified working end-to-end**, tested by reconstructing a valid signed payload in-browser (`crypto.subtle` HMAC-SHA256, same algorithm as `src/utils/qrPayload.ts`) rather than a camera, since headless Playwright can't drive a real camera:

- `QRDisplay.tsx` renders a real QR canvas (`qrcode` npm package, no external dependency) encoding `{playerId, missionId, sessionId, xpValue, issuedAt, hmac}` as base64 inside a `/validate/:sessionId?t=` URL.
- `ValidationPage.tsx` correctly decoded a manually-crafted valid token, verified the HMAC, and displayed the right milestone/mission/player/XP.
- Clicking "Confirm" invoked the write path (`useValidationConfirm`) and navigated back to Admin Home as expected.
- A real (non-demo) PocketBase session confirmed to have a genuine, correctly-generated `qrSecret` (64-char hex, from the Go `OnRecordCreate` hook) — the server side of the QR mechanism is real, not stubbed.

**Two minor gaps, not blockers:**
- `ValidationPage.tsx:189-192` shows the player as a raw UID (`uid_sofia_002`) instead of a resolved name — cosmetic, but confusing for a GM validating in the field.
- The *admin invite* QR (separate from mission QR) in `SessionInviteCard.tsx` loads its QR renderer from an external CDN (`cdnjs.cloudflare.com/.../qrcodejs`) rather than the bundled `qrcode` package already used elsewhere. In a network-restricted deployment this QR silently fails to render (we hit exactly this failure mode testing an unrelated CDN script in this session) — the copyable text link still works as a fallback, but it's an avoidable single point of failure for a QR-code-first product.

I was not able to independently re-verify that a confirmed QR write *persists* after reload for the demo/mock path — every hard page navigation resets the mock adapter's in-memory store by design (documented, not new), and a full production re-test needs a real PB hire with an actual joined player, which is blocked by finding 1.1. Worth re-running this specific check once 1.1 is fixed.

## Priority punch list

1. **Fix the hire-creation navigation race (1.1)** — this blocks every new hire from being usable through the UI at all; highest priority by far.
2. **Reconcile the two invite mechanisms (1.2)** — decide which is canonical, delete or wire up the other.
3. **AI assistant latency/false-failure on first message (2)** — either speed up cold-start RAG/reranking or fix the client-side handling so a slow-but-successful response doesn't show as failed.
4. **Silent failure on orphaned local identities (1.3)** and **CDN dependency for admin invite QR (3)** — smaller robustness fixes.
